一、当前基础

目前项目有371张插画，覆盖372篇菜谱：
- catalog/nutrition.json 已存在，目前只有水煮玉米有营养参考。
- public/manifest.json 和 manifest-lite.json 已包含 nutrition 字段。
- 其他菜品多数为 unknown。

保留现有稳定 key、recipe_ids、图片摘要地址及公开 JSON 兼容性。营养原始资料与映射应维护在源数据中，再由构建脚本生成公开文件，不直接手改构建产物。

二、数据来源

优先使用 USDA FoodData Central：
- API：https://fdc.nal.usda.gov/api-guide/
- 官方批量数据：https://fdc.nal.usda.gov/download-datasets/

可以选择批量下载或 API，但不要逐条重复请求已有数据。建立可复用的原始响应缓存，保留来源版本、FDC ID、来源网址和获取日期。

USDA 数据为公共领域、CC0，更新项目来源说明，明确本项目是独立整理的参考数据，不是 USDA 官方产品。

若使用 API：
- Key 只放本地未跟踪的环境文件或 CI Secret。
- 不得进入浏览器代码、公开 JSON、Git、日志或测试快照。
- 提供 .env.example 和配置说明。
- 控制请求频率，处理429、超时和重试，支持断点续跑。
- 若缺少 Key，可先使用官方公开下载数据完成不依赖 Key 的工作。

三、营养匹配与计算方式

不要假设每道中国菜都能在 USDA 找到完全对应的成品。

分两种方式处理：

1. 直接营养参考
适用于能找到合理对应项的食物。
必须核对食物种类、部位、生熟、烹饪方式、可食部分、品牌等关键条件。
不能直接拿搜索第一项，也不能只因名字相似就通过匹配。

2. 配方营养估算
没有合理成品参考时，根据具体菜谱拆分食材，各食材分别匹配 USDA，再计算：

食材营养 = 食材每100g营养 × 可食克数 ÷ 100
整份配方营养 ≈ 各食材营养之和
成品每100g营养 ≈ 整份配方营养 ÷ 成品可食总重量 × 100

注意：
- 食材重量、生熟状态和营养基准必须一致。
- 明确加入的油、糖、酱料等需要纳入。
- 毫升转克需要有依据的密度，不能统一按1ml=1g。
- 带骨、带皮、玉米芯等需要明确可食部分。
- 成品重量不能直接当作原料重量之和，尤其是吸水、失水、沥水、油炸等情况。
- 有可靠烹饪保留率或出成率时可以使用，并保存依据。
- 没有做烹饪损失校正时，明确记录该假设；影响较大且无法合理估算时保持待补充。
- 可选配料、数量区间及默认取值必须明确记录，不能静默补齐。
- 不把整锅营养当作每100g营养。

模型可以辅助提取食材、转换检索词和推荐匹配候选，但不能凭空生成营养数字、FDC ID、来源或假装完成审核。

四、营养数据设计

兼容现有 nutrition 结构，优先采用兼容追加字段；确需破坏性变化时提供新版本及迁移说明。

需要表达：
- 营养状态和审核状态。
- 计算方式：USDA直接参考或基于USDA食材的配方估算。
- 每100g成品可食部分的热量、蛋白质、碳水、脂肪。
- 适用范围：生熟、做法、是否含油酱、品牌、排除条件。
- 对应 recipe_id、配方版本及默认假设。
- USDA来源、FDC ID、数据类型、版本和获取日期。
- 配方估算的各食材克数、来源及成品重量依据。
- 计算规则版本、不确定性和审核证据。

完整溯源可以放到按需加载的独立详情文件，轻量目录只保留运行时匹配和计算需要的摘要。

不要把插画 key 当作唯一营养配方标识。同一插画对应不同配方时，应分别保存营养方案；只有存在合理通用参考时才设置默认营养。

未知值保持 null，不能填0或伪造完整数据。已有有效参考不要无依据覆盖。

五、面向其他应用的使用规则

使用方应能够判断：
- 是否有可用营养参考。
- 参考适用于什么食物及做法。
- 是直接参考还是配方估算。
- 使用了哪个版本和来源。
- 数据不适用或未知时，需要转到其他数据源查询。

图片匹配可以相对宽松，营养匹配必须独立校验。
例如糯玉米可以使用相近的玉米插画，但不能因此自动使用黄色甜玉米粒的营养。

所有营养数据都属于参考或估算，不代表用户实际吃下的精确配方。

六、覆盖与执行方式

目标是逐步评估全部372篇菜谱，不只做少量演示。

建立覆盖报告，区分：
- 已有可用直接参考。
- 已有可用配方估算。
- 已找到候选但待核验。
- 缺少用量、成品重量或适当来源。
- 无合理匹配。
- 请求失败、待重试。

支持分批、断点续跑，并缓存已完成工作。
不要因为难匹配而跳过不记录，也不要为了完成率强行填数。
候选生成完成不等于营养审核完成，公开目录不得静默使用待审核候选。

对条件清晰、证据充分的项目自主推进；仅对无法可靠确定的部分保留具体待办，无需每个条目都向我确认。

七、验收与交付

补充有意义的数据校验和测试：
- 数值有限、非负、单位正确。
- 缺失营养不能默认为0。
- 每100g与整份换算正确。
- 每个营养素独立处理未知，部分已知不能冒充完整。
- FDC ID、来源和配方映射可追溯。
- 同图不同配方不会误合并。
- 重跑不产生重复数据。
- API失败不会覆盖已有效数据。
- 公开 JSON 兼容现有接入方式。

4/4/9可以作为合理性检查，但不要强行改写USDA热量，让它必须与宏量营养折算完全一致。

按 AGENTS.md 执行构建和检查；如果修改网站展示，补做对应界面验收。不要擅自推送或部署。

在 README 或 docs 中说明：
